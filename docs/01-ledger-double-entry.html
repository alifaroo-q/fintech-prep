Module 01 · immutable double-entry core

The balance is a sum of entries, and Postgres rejects an unbalanced sum at COMMIT

Each debit and credit is an append-only row. A deferred constraint trigger checks debits − credits = 0 when the transaction commits, so no unbalanced row survives, even with 20 writers at once.

Why derive

A stored balance loses writes; a summed balance cannot

The column also forgets. It cannot say what the balance was on 3 March, or why it is what it is. The entries carry effective_at, so balanceOf(db, id, asOf) answers that with a filter.

The cost: a read scans every entry for the account. At scale, add periodic checkpoints and sum only the newer entries. A check such as “cash must not go negative” still needs a row lock or SERIALIZABLE; module 04 adds that.

Schema

Three tables, four database rules

  1. ① entries_balanced: constraint trigger, DEFERRABLE INITIALLY DEFERRED, raises LG001.
  2. ② transactions_balanced: the same check from the header, so a header with 0 entries also fails.
  3. ③ CHECK (amount > 0): the sign lives in direction; integer minor units only.
  4. ④ UPDATE, DELETE and TRUNCATE on both ledger tables raise LG002. Corrections are new reversing transactions.

Proof

The tests fail when the triggers go

A green suite alone does not show what it checks. With the entries trigger immediate, the separate-statements test fails first. A one-statement posting still passes, because a row trigger that is not deferred fires at the end of the statement.

Gaps

Five things the suite does not cover yet

not sealed

A later session can add a balanced pair to a committed transaction. The sum stays 0, but the posted transaction changes.

O(n²)

The trigger fires once per entry and sums all entries each time.

no helper

reverses_transaction_id exists, with no reversal function or test.

as-of only

balanceOf filters on effective_at, not recorded_at.

outcome only

The cross-session test does not check whether session B blocks or fails at once.
